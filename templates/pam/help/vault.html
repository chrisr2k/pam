The Vault

The vault stores secrets — passwords, SSH private keys, API tokens — encrypted, and lets you check them out temporarily instead of having them permanently. When a checkout ends, entries flagged for auto-rotation get a brand new random value, so any secret you saw becomes worthless.

How to use a secret
  1. Find it under Roles — vault entries appear as roles named Vault: <name>.
  2. Request a checkout exactly like any access request (justification + duration, approval if the entry requires it).
  3. When the checkout is active, open the entry (via the role page's Reveal Secret button or the entry link) and click Reveal Secret.
  4. If you're enrolled in MFA, confirming your code is required.
  5. The secret is shown once. Copy it immediately — after you leave the page it cannot be shown again without another reveal (each reveal is audited).
  6. The checkout expires automatically (or you can revoke it). If the entry auto-rotates, the revealed value is already dead.
Rotation plugins — syncing to the real system

By default, "rotation" means the vault generates a new random value and stores it — the target system is not touched. For entries configured with a rotation plugin, rotation actually reaches out and changes the credential on the real system (like CyberArk's CPM):

  • AWS IAM access key — the entry holds the user's access key pair as JSON. Rotation creates a new key, verifies it works, stores it, then deletes the old key. For a brief moment the user has two active keys (never zero).
  • Entra app client secret — rotation adds a new client secret to the app registration, stores it, then removes the old one. (The app needs the Application.ReadWrite.OwnedBy permission to rotate its own credentials.)
  • SSH (Linux/Unix) — changes the account password over SSH via chpasswd (config: host, username; optional use_sudo).
  • PostgreSQL — ALTER USER with the account's current password (config: host, username).
  • MySQL — ALTER USER, MySQL 8+ / MariaDB 10.2+ (config: host, username, optional host_part).
  • Windows (WinRM) — net user (local) or Set-ADAccountPassword (AD) over WinRM (config: host, username, optional account_type).
  • Generic HTTP webhook — POSTs the new value to a URL with {old_value}/{new_value} templates, optional verify/cleanup requests (config: url).

Password plugins (SSH, databases, Windows, HTTP) generate the new value before anything is changed, then apply → verify → store, with a best-effort rollback to the old password if verification fails. If rotation fails, the existing value is kept — the vault never stores a credential the target system doesn't have. Failures are shown in the rotation history.

Good to know
  • Why checkouts? Anyone with a checkout is visible, time-limited, and audited — exactly the audit trail permanent passwords lack.
  • Auto-rotation: when a checkout ends, the vault rotates the secret — a fresh random value for vault-only entries, or a real system credential change for plugin entries.
  • Rotation breaks old copies: after rotation, any previously revealed or exported value stops working immediately. Don't use auto-rotation on entries other live systems still depend on — coordinate with your admins.
  • Reveals are logged (who, which entry, when — never the value). Misuse is detectable.
  • Several people can hold checkouts for the same entry at once; each reveal and rotation is tracked separately.
